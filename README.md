## Что это

NanoDecompiler берёт `.jar` скомпилированного плагина или мода и превращает
его обратно в читаемый Maven-проект: настоящие `.java`-файлы с пакетной
структурой, восстановленный (или найденный оригинальный) `pom.xml`,
ресурсы плагина рядом с кодом — всё так, как будто открываешь исходники
автора, а не байткод.

Инструмент целиком **desktop, без Python** — Electron-приложение
на React поверх собственного декомпилятора на C++17. Сам jar никогда не
покидает ваш компьютер. Из коробки приложение обращается к сети только за
номером новой версии (api.github.com); всё остальное — см. «Приватность».

## Приватность

Что приложение может отправлять в сеть и когда:

| Функция | По умолчанию | Что уходит и куда |
|---|---|---|
| Проверка обновлений | включена | запрос версии к `api.github.com` (виден ваш IP); отключается в настройках |
| Проверка легитимности плагинов | **выключена** | название/автор плагина → GitHub, Modrinth, Spiget, Hangar, SpigotMC.ru; список сайтов подтягивается с `raw.githubusercontent.com` |
| Отправка отчётов об ошибках | **выключена** | имя jar/плагина, версии, ОС, статистика и короткие фрагменты декомпилированного кода вокруг мест с байткодом → сервер разработчика (HTTP). Полные исходники файлов — только по ручной кнопке в карточке плагина |
| Поиск похожих репозиториев | только по клику | название/автор плагина → api.github.com |
| Экспорт в GitHub | только по клику | декомпилированный проект → ваш репозиторий на GitHub (токен передаётся только в окружении процесса git и нигде не сохраняется) |

Пока вы не включили соответствующий переключатель в «Настройках» (и в мастере первого запуска), ничего, кроме запроса версии, не отправляется. Свой сервер отчётов можно указать переменной окружения `NANO_TELEMETRY_URL` (желательно HTTPS), секрет сервера — `NANO_TELEMETRY_SECRET`.

## Возможности

**Движок**
- Честный откат на байткод там, где нельзя восстановить код безопасно
  (`DecompileAbort`) — лучше видимый TODO-комментарий, чем красиво
  оформленная выдумка, которая на самом деле не то, что писал автор.
- Определение платформы (Bukkit/Spigot/Paper/Velocity/BungeeCord/Fabric/
  Forge/NeoForge) с честным «неизвестно», если манифест платформы не
  найден — вместо угадывания наугад.
- Фильтрация бандленных сторонних библиотек (Guava, Gson, Netty, H2,
  bStats и десятки других) — в выводе только код самого плагина.
- Находит вложенные `.jar` там, где они есть, — с одним кликом
  «декомпилировать тоже».
- Эвристический скан на признаки вредоносного кода и легитимность
  (совпадение с известными хэшами/паттернами) — эвристика, не гарантия,
  явно так и помечено.
- Восстановление читаемых имён вместо `a`/`b`/`method1`, распознавание
  `switch(String)`, литералов массивов, enum-констант, record-классов —
  и осторожная граница там, где переименование рискует сломать компиляцию
  обратно.

**Интерфейс**
- Настоящее дерево файлов — раздельные секции Java-пакетов и ресурсов,
  вложенность по сегментам пакета (как в любой нормальной IDE, не одной
  строкой на весь dotted-путь), сортировка по имени/размеру/предупреждениям,
  поиск по имени И по пакету, collapse-состояние переживает перезапуск.
- Подсветка синтаксиса Java + отдельная подсветка Minecraft-цветовых кодов
  (`§`/`&`, `ChatColor.RED`, кастомные цветовые методы) прямо в коде.
- Карточка плагина с деталями: статистика декомпиляции, найденные
  библиотеки, конфликты импортов, находки малварь-скана — без необходимости
  листать терминал в поисках того, что уже загружено.
- Палитра команд (`Ctrl+K`), кроссплатформенная сборка (Windows/macOS/Linux).
- **Модульные OTA-обновления**: дифференциальная доставка обновлений (микро-модули интерфейса и ядра) без необходимости перекачивать 100 МБ инсталлятор при каждом патче.
- **Web / WASM Edition (`docs/web_decompiler.html`)**: полноценная клиентская декомпиляция в браузере (на ПК и смартфонах) с декодированием постоянного пула, разбором байткод-инструкций и детекцией NanoGuard без отправки файлов на сторонние серверы.

## Как это выглядит

Терминальный брендинг (true-black фон, кислотно-зелёный акцент, моно-шрифт
для лога) поверх структурных приёмов Material Design 3 (elevation,
скруглённые surface-контейнеры, tonal-кнопки) — не смешение ради
смешения, а осознанное продолжение того, с чего проект начинался в
Tkinter/CustomTkinter-эпоху (`gui_neon.py` в v1.2), перенесённое в
современный стек.

## Запуск из исходников

Нужен Node.js 18+ и C++17-компилятор (g++/clang++) — Python для сборки
или запуска проекта не требуется вообще.

```bash
# 1. Собрать движок
cd resources/engine_cpp && cmake -S . -B build && cmake --build build --parallel
cp build/NanoDecompilerCLI ../engine/NanoDecompilerCLI   # .exe на Windows
cd ../..

# 2. Установить зависимости и запустить
npm install
npm start          # соберёт всё и сразу откроет окно Electron
```

Для разработки с hot-reload — `npm run dev` (поднимет Vite dev-server) в
одном терминале и `npm run build:electron && npx electron .` в другом.

## Сборка дистрибутива

```bash
npm run dist
```

`electron-builder` соберёт установщик и включит `resources/engine/` как
`extraResources` — туда нужно заранее положить собранный бинарник движка
(CI делает это автоматически, см. `.github/workflows/build-and-release.yml`).

## Структура проекта

```
electron/              # main process + preload (TypeScript)
src/                    # React renderer (Vite + Tailwind)
resources/engine_cpp/   # C++-движок декомпиляции (свой README.md)
resources/engine/       # HANDOFF_*.md - подробная история разработки движка
scripts/                # вспомогательные скрипты сборки/тестового окружения
CHANGELOG_*.md          # changelog по версиям
```

Подробнее про устройство самого движка (модули, эвристики, честные
ограничения) — `resources/engine_cpp/README.md`.

## Честность как принцип

Инструмент нигде не претендует на то, что не может гарантировать:

- если код нельзя безопасно восстановить — вы увидите байткод с честным
  комментарием, а не правдоподобно выглядящую догадку;
- если платформа не опознана — так и написано, «неизвестно», а не
  наугад выбранный вариант;
- находки скана на малварь — это эвристика по документированным
  паттернам, а не гарантия чистоты или вредоносности файла;
- сгенерированный `pom.xml` явно помечен как восстановленный, а не
  оригинал автора, если только оригинал не был реально найден внутри jar.
